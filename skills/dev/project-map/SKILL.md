# Project Map · 项目文档地图

从当前代码建立可追溯的项目地图，让人和后续 Agent 能回答：**功能如何运行、代码按什么职责组织、每个文件有哪些函数、改一个需求应该从哪里入手。** 默认中文，标识符保留原名；遵循用户指定的文档语言。

## 使用方式

| 用户意图 | 执行范围 |
| --- | --- |
| “整理整个项目”“生成项目文档” | 首次全量建图，覆盖范围内全部自有源码和测试 |
| “更新项目地图”“同步最近修改” | 核对已有文档基线，更新变化及其调用方、被调用方和关联功能 |
| “只整理订单模块” | 仅整理指定范围，标明与外部模块的边界及未展开部分 |

先从请求、仓库约定和已有文档确定范围。用户没有指定时，默认当前项目、全部自有源码、逐文件逐函数；已有项目地图则先检查是否可增量更新。只在项目边界或写入位置存在实质歧义时询问。

## 交付位置

优先沿用项目现有的同类文档组织方式；没有时写入 `docs/project-map/`。写文档前读取 [文档结构与字段](references/document-layout.md)，落实其中的覆盖表和函数表。

- `README.md`：项目概览与文档导航。
- `DIRECTORIES.md`：目录职责、文件清单与功能归属。
- `FEATURES.md`：功能入口、执行流程、调用关系与数据流。
- `modules/`：按实际源码目录组织的逐文件、逐函数说明。
- `CHANGE-GUIDE.md`：需求到修改位置、影响范围和验证点的映射。
- `COVERAGE.md`：阅读覆盖、代码基线、排除项与待核实项。

业务事实放在对应模块文档，其他页面用链接引用。模块文档的路径保持目录层级，避免同名目录碰撞，例如 `modules/apps/api/src/orders.md` 和 `modules/apps/web/src/orders.md`。

## 工作流程

### 1. 确认代码快照与清单

读取项目约定、现有文档和入口配置，确认项目根目录、工作区/子项目、主要语言、构建方式及文档位置。旧文档提供线索；与代码冲突时，以当前代码为准并记录差异。

建立文件清单，纳入已跟踪文件和未被忽略的新文件，保留隐藏的构建/CI 配置。对范围内每个文件登记处理状态；目录层面可集中登记第三方依赖、构建产物、生成代码和二进制资源的排除原因。配置、迁移、脚本、测试及无函数源码同样需要交代用途。子模块和指向范围外的符号链接只登记边界，不自动扩展扫描。

在 `COVERAGE.md` 记录日期、范围、枚举方法、当前 revision（能取得时）、工作区是否有修改及其路径。没有 Git 时照常全量读取，明确写明无 Git 基线。凭据文件只登记存在性及代码引用，不复制值。

**本步完成条件：** 候选文件均已列入清单或有明确排除规则，尚未读取的对象有待处理状态。

### 2. 先建立符号索引，再解释职责

逐文件读取代码，先枚举符号再撰写说明。可用语言服务、AST 或现成解析器交叉核对；正则搜索只用于发现候选，不作为完整覆盖的证明。

覆盖命名函数、私有辅助函数、类方法、构造函数、嵌套函数、赋给变量的箭头函数/lambda，以及组件、hook、命令处理器等可调用定义。使用限定名区分同名符号，例如 `CheckoutService._normalize.valid`。重导出、别名与实际实现分别指明；重要匿名回调说明归属及触发条件。类型、常量、配置文件按职责描述，无函数的文件明确标记。

每个函数说明用途、主要输入输出、副作用、调用关系和相关测试；普通函数一行即可，跨模块入口和复杂逻辑再展开。不把名称或注释的猜测写成实现事实。

**本步完成条件：** 清单内每个已核源码文件都有函数清单或“无函数”说明；符号总数与索引一致，未完成文件保留待处理状态。

### 3. 按功能追踪执行和数据流

从实际入口（页面、路由、CLI、任务、事件或库的公开 API）向下追踪核心功能：触发条件 → 入口符号 → 编排逻辑 → 规则/存储/外部系统 → 返回结果或副作用。

每条功能链关联具体目录、文件和符号，区分同步调用、异步任务、事件发布与订阅。导入依赖不等于运行调用；配置声明不等于已经装配的运行入口。对动态注册、依赖注入、反射和仓库外实现，说明已找到的装配证据；链路断点标为待核实。

目录职责从实际调用与数据归属归纳。对于一个功能跨多个目录、一个目录服务多个功能的情况，保留多对多映射，勿强行把目录当成功能边界。

**本步完成条件：** 已识别功能都有入口、主要步骤、目录映射及源码依据；无法确认的连接显式登记。

### 4. 给出后续修改导航

针对项目实际存在的需求类别，列出：优先修改的文件/符号、为什么从这里开始、需要核对的调用方/数据契约/配置、相关测试或验证场景，以及改动后要同步的地图页面。

提供至少一条可直接交给 Agent 的修改指令，包含目标行为、已确认的入口、影响范围和验证要求。源码中尚未实现的功能，写明需要先设计或定位的边界；避免把建议模块描述成现有实现。

### 5. 验证并交付

- 对照文件清单核对覆盖表和函数表；“全部覆盖”只用于没有待处理源码的范围。
- 检查文档链接、源码路径、限定名和引用行号；源码链接优先用相对路径，行号仅作本次快照定位。
- 抽查功能链的关键连接，确认修改导航引用的实现和测试真实存在；区分已有测试与建议新增的场景。
- 记录实际采用的静态分析或验证方式；静态读码不能证明运行正确性，也不等于执行过测试。
- 默认仅修改文档，保留现有人工说明。不通过整理任务改业务代码、安装依赖、改 Agent 全局规则或自动提交。

最终回复文档入口、实际覆盖的文件/函数数量、主要待核实项和一次后续更新的调用示例。大项目分目录持续落盘；若本轮无法完成，交付已完成部分和剩余路径，清楚标为部分覆盖，不能擅自缩为“核心文件”后宣称完整。

## 增量更新

先读取地图索引与 `COVERAGE.md`，重新枚举文件，处理新增、修改、删除、重命名及失效链接；沿引用关系检查受影响的功能链和修改导航。

有可靠 Git 基线时比较到当前工作区，包含暂存、未暂存和未被忽略的新文件。上次记录为脏的文件也要重新核对，不能只按当前 `git diff` 判断变化。无可靠基线、范围变化或既有文档缺少覆盖记录时，对相关范围重新建图。

未重新阅读的文件保留上次核对状态与日期，明确本次检查集合。只有已处理全部候选变化及关联文档后，才推进覆盖基线；不要给未复核内容统一盖上本次日期。

## 工具与平台

优先使用宿主的检索、读取和语言分析能力，本 skill 无必装脚本或解析包。首次使用外部命令前探测能力并记录结果；区分“本平台不存在”“存在但执行失败”“探测失败”。失败时转用已确认的宿主能力，或将受影响范围登记为未核并给出恢复动作；环境问题出现后停止同类批处理。

macOS 与 Windows 都可以通过宿主读文件完成静态建图。解析器缺失时逐文件阅读并注明核对方法；不要临时安装工具、导入执行项目模块来提取符号，或依赖某一平台专有命令完成核心流程。
