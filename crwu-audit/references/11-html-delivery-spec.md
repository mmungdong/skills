## 1 目标与适用范围

本规范用于统一 CRWU 审核系统的结果数据、员工送达页面与审计追溯口径。无论审核由多少个叶子 Skill、规则包或校验模块参与，每次审核最终只向员工交付一个可离线打开、可打印、可追溯的 HTML 文件。

### 1.1 目标

- 让普通员工在首屏快速判断“有没有问题、先处理什么、去哪里修改、为什么”。
- 让三级审核与质控在同一文件内追溯每个结论使用的规则、被审核材料、差异推导和复核来源。
- 让维护者能够还原本次实际装载和命中的规则、知识库文件版本及检查覆盖情况。
- 把审核判断与页面渲染解耦，避免不同 Skill 输出口径、术语和版式各自演进。

### 1.2 适用范围

| 适用对象 | 适用内容 |
| --- | --- |
| 叶子 Skill | 按统一字段契约输出规则命中、材料证据、裁定与检查记录。 |
| 审核编排器 | 汇总结果、执行门禁、冻结阶段一、完成阶段二对照并产出 AuditResult。 |
| HTML renderer | 将 AuditResult 确定性渲染为单文件 HTML。 |
| 规则库维护 | 维护权威层级、版本、条款、来源路径和 exportedAt。 |
| 三级审核与质控 | 核对结论、复核差异、未检查项和证据完整性。 |

### 1.3 不在本规范范围内

- 不规定具体资产评估结论或真实法规条款内容。
- 不替代规则库的规则编写规范、统计台账规范或项目业务方案。
- 不允许 renderer 推断、补齐或重新裁定业务结论。

## 2 核心原则

| 原则 | 强制口径 |
| --- | --- |
| 一个交付文件 | 员工侧每个项目只接收一个 HTML。JSON 可嵌入同一 HTML，不作为额外交付件。 |
| 一个事实源 | AuditResult JSON 是唯一权威结果。页面、打印版和汇总均从它派生。 |
| 双证据链 | 审核规则依据回答“凭什么审”；被审核材料证据回答“从哪里发现”。二者不得合并成模糊的“依据”。 |
| 五段式判定 | 每条问题按规则、材料、差异、结论、修改形成闭环。 |
| 两阶段隔离 | 阶段一独立审核不得读取或参考复核记录；阶段一冻结后，阶段二才进行复核对照与综合比较。 |
| 权威分层 | 外部正式依据与内部辅助规则必须显著区分，内部 Markdown 不得被描述成法规或准则。 |
| 展示分层 | 员工任务优先，工程字段和审计细节默认折叠，但不得丢失。 |
| 诚实覆盖 | 不可读、未实现、缺材料或未执行的检查必须显式列入未检查项。 |
| 只呈现不改写 | renderer 不新增、删除、合并、拆分、升级、降级或润色审核结论。 |

## 3 最终交付结构

员工界面严格采用以下顺序。前四部分解决员工工作任务，第五至第七部分解释依据和边界，第八部分服务专业复核，第九部分完成文件级追溯。

| 序号 | 页面区域 | 默认状态 | 主要回答 |
| --- | --- | --- | --- |
| 01 | 项目信息 | 展开 | 这是哪个项目、哪个版本、何时审核。 |
| 02 | 审核结果概览 | 展开 | 是否通过、问题数量和优先级。 |
| 03 | 需要处理的问题 | 展开 | 改什么、为何、去哪里改。 |
| 04 | 需要人工确认事项 | 展开 | 哪些尚不能作为确定结论。 |
| 05 | 本次审核依据 | 展开/分组 | 本次实际用了哪些正式与内部规则。 |
| 06 | 人工复核对照 | 展开 | AI 与人工复核是否一致。 |
| 06b | 本次 AI 审核六维评分卡 | 展开 | AI 自评六维分数、复审校正与 AI 审核错误项（**表格呈现**）。 |
| 07 | 审核范围与未检查项 | 展开 | 检查了什么、没检查什么及影响。 |
| 08 | 专业审核轨迹 | 默认折叠 | 规则快照、逐条裁定、完整检查记录和综合对比。 |
| 09 | 文件追溯信息 | 展开 | 数据版本、生成时间、完整性校验和工具版本。 |

### 3.1 员工端术语映射

| 内部术语 | 员工界面用语 | 展示说明 |
| --- | --- | --- |
| A | AI 与人工复核均发现 | 相互印证 |
| B | 仅 AI 发现 | AI 新增发现，建议人工确认 |
| C | AI 与复核均涉及但结论或范围不同 | 结论存在差异，需复核 |
| L / 复核独有 | 仅人工复核发现 | AI 未命中，先做在件核验（见 §6.1）再定性 |
| CHK | 检查点 | 仅在专业审核轨迹显示 |
| kb_id | 规则编号 | 在依据详情显示，不抢占卡片标题 |

## 4 问题条目规范

### 4.1 分流与排序

- “需要处理的问题”按高、中、低排序；同等级内按业务分区、文件顺序和定位排序。
- 规则性缺陷与已有充分材料依据的合理性问题进入处理区。
- 无依据待判、证据不足或必须由专业人员判断的事项进入“需要人工确认事项”，不得包装成确定性不通过。

### 4.2 每条问题的最小字段

| 字段 | 必填 | 员工展示 | 要求 |
| --- | --- | --- | --- |
| issueId | 是 | 是 | 稳定且项目内唯一。 |
| title | 是 | 是 | 一句话说明具体问题，不使用内部代号代替。 |
| module | 是 | 详情 | 归因模块。 |
| locationSummary | 是 | 是 | 首要文件、分区与定位摘要。 |
| severity | 是 | 是 | high / medium / low。 |
| issueType | 是 | 是 | rule_defect / reasonableness_doubt / unsupported_pending。 |
| decision | 是 | 是 | fail / pending_confirmation / pass；问题列表通常不记录 pass。 |
| problemDescription | 是 | 是 | 客观陈述，不补写材料中不存在的事实。 |
| handlingRequirement | 是 | 是 | 必须修改 / 补充说明 / 核实后处理 / 人工确认。 |
| ruleEvidence[] | 条件必填 | 是 | 不通过为规则性缺陷时至少一条正式或明确分层的辅助依据。 |
| materialEvidence[] | 是 | 是 | 至少一条真实读取的文件内证据。 |
| gapAnalysis | 是 | 是 | 规则要求、材料现状、差异和判断的明确映射。 |
| recommendedEdits[] | 是 | 是 | 具体到建议修改文件、位置和动作。 |
| flowStatus | 是 | 是 | 待答复 / 已答复 / 已复核。 |
| confidence | 是 | 详情 | 高 / 中 / 低及理由。 |
| reviewComparison | 阶段二必填 | 是/详情 | 未进入阶段二时必须标明未执行。 |

### 4.3 双证据链

规则侧证据与材料侧证据必须分别存储、分别展示、分别引用。一个问题只有规则而没有材料，只能说明“应当如何”，不能证明本项目“实际违反”；只有材料异常而没有适用规则或明确的专业判断边界，不得直接形成规则性缺陷。

| 证据链 | 允许来源 | 最小定位 | 关键字段 |
| --- | --- | --- | --- |
| 审核规则依据 | 法律法规、资产评估准则、评估方法规则、监管规则、协会要求、内部审核规则、CRWU 知识库规则、历史风险案例 | 规则名称 + 版本 + 条款；知识库相对路径 + exportedAt | authorityClass、sourceType、ruleId、title、version、clause、quote、kbRelativePath、exportedAt |
| 被审核材料证据 | 报告正文、评估说明、测算明细表、附件、答复材料等本次实际读取文件 | 文件名 + 页码/章节/段落或 Sheet + 单元格/区域 | fileId、displayName、section、locator、excerptOrValue、evidenceRole、contentHash（可选） |

### 4.4 五段式判定链

1.  规则：陈述适用于本项目的要求，并引用规则条款与来源。

2.  材料：列出实际读取到的文件证据、位置和原文或数值。

3.  差异：逐项解释材料与要求之间的不一致、缺失或无法验证之处。

4.  结论：给出不符合、需人工确认或其他限定结论，并匹配严重程度与意见类型。

5.  修改：明确处理要求、建议修改文件、定位与可执行动作。

### 4.5 判定纪律

- 引用原文应逐字一致；转述必须显式标注为“转述”。
- 一个差异引用多个文件时，两端证据均需列出；跨表勾稽应同时给出两个或多个坐标及数值。
- 建议修改文件不得凭经验猜测；不能确定时写“请项目负责人确认修改载体”。
- 严重程度用于表达影响与处理优先级，不得代替依据强度。
- 低置信度或证据不足不得通过措辞强化为确定性结论。

## 5 本次审核依据规范

“本次审核依据”只列入本次实际装载且被检查流程使用的规则。命中问题的规则记录引用次数与用途；仅参与覆盖检查但未形成问题的规则，可记录用途为“覆盖核查”或“符合性确认”。不得把整个知识库目录无差别列入。

### 5.1 权威层级

| 权威类别 | 典型来源 | 员工标签 | 使用边界 |
| --- | --- | --- | --- |
| external_formal | 国家法律法规、有效监管规定、正式资产评估准则、行业协会正式要求 | 外部正式依据 | 可以在适用且证据充分时支撑规则性缺陷；仍须核验版本、适用场景和条款。 |
| internal_auxiliary | 公司内部审核规则、CRWU 知识库规则、内部检查清单 | 内部辅助规则 | 用于内部质量控制、发现线索和统一检查口径；不得冒充法规、监管规定或行业准则。 |
| experience_reference | 历史风险案例、回测案例、经验规则 | 历史风险经验 | 用于提示类似风险和反查；原则上不能单独证明外部不合规。 |

### 5.2 规则来源分类

- 法律法规
- 资产评估准则
- 评估方法规则：市场法、成本法、收益法及其他适用方法
- 监管规则
- 行业协会要求
- 内部审核规则
- CRWU 知识库规则
- 历史风险案例

### 5.3 规则记录字段

| 字段 | 说明 |
| --- | --- |
| ruleId | 稳定规则编号或 kb_id。 |
| authorityClass | external_formal / internal_auxiliary / experience_reference。 |
| sourceType | 上述规则来源分类。 |
| title | 正式规则或内部规则名称。 |
| version | 本次实际使用版本；无法确认时不得写“现行”。 |
| clause | 具体条款、检查点或案例节点。 |
| effectiveStatus | effective / expired / unknown / internal。 |
| quote | 本次使用的逐字原文；转述时另设 paraphrase。 |
| kbRelativePath | 相对知识库根目录的路径，不得为本地绝对路径。 |
| exportedAt | 本次读取或导出的知识库版本时间。 |
| usageCount | 被意见条目或检查记录引用的次数。 |
| purposes[] | 如报告披露、成本法参数、证券监管覆盖、风险反查。 |
| usedByIssueIds[] | 引用该规则的问题编号。 |
| sourceFingerprint | 可选，来源内容哈希或版本指纹。 |

### 5.4 审核规则地图

规则地图是“本次审核依据”的可读导航，不是新的事实源。它由规则记录按权威层级、业务对象、评估方法和监管覆盖层聚合生成。建议显示如下层级：

```text
外部正式依据
├─ 资产评估准则
│  ├─ 资产评估基本准则（2017）〔示意〕
│  └─ 资产评估方法相关准则（版本待实际读取）
├─ 评估方法
│  └─ 成本法：重置成本、实体性贬值、经济性贬值
└─ 监管规则
   └─ 证券业务：本次命中条款

内部辅助规则
├─ CRWU 企业价值审核清单
└─ 成本法参数一致性检查

历史风险经验
└─ 相似风险案例：2 项
```

示例中的“2017”、规则名称和项目方法仅用于说明展示方式。生产输出必须从 AuditResult 的实际规则记录生成，不得硬编码。

## 6 人工复核对照

人工复核对照是阶段二产物。系统必须先保存阶段一冻结标识、冻结时间和结果摘要，再允许读取复核记录。阶段二不得回写或伪装成阶段一发现。

### 6.1 双向三条带与漏检反查

| 内部分类 | 员工展示 | 处理 |
| --- | --- | --- |
| A / overlap | AI 与人工复核均发现 | 展示两端出处，说明相互印证范围。 |
| B / ai_only | 仅 AI 发现 | 保留 AI 证据，提交人工确认；不能因人工未记录而自动撤销。 |
| C / divergent | AI 与人工复核均涉及但结论或范围不同 | 列出差异点，不自动选择一方。 |
| L / reviewer_only | 仅人工复核发现 | 先做「在件核验」再定性（下表三态）；不得直接当漏检计入。 |
| L-resolved | 复核已提出 · 被审件已落实 | 计为人工工作成果；不计漏检、不进命中率分母。 |
| L-open | 复核已提出 · 被审件未落实 | 真漏检候选，进隔离补审。 |
| L-unclosed | 复核答复称已改 · 被审件未落地 | 复核闭环失效，优先回客户。 |
| L-uncheckable | 材料缺失或不可读 · 未能核验 | 记未检查项，不臆断。 |

### 6.2 对照证据要求

- AI 侧必须引用阶段一已冻结的 issueId 和原始证据。
- 复核侧必须给出复核文件、定位和原文摘录，不得仅写“人工也发现”。
- 匹配理由应说明同一问题、部分重合或仅主题相似，禁止关键词相似即判定一致。
- **在件核验证据**：每条复核独有项定性前必须给出**被审件在件位置**（`inFileEvidence.file` + `locator`）；
  未做在件核验的，不得计入漏检，也不得计入命中率。`L-unclosed` 另须给出**答复出处**（`closureEvidence`）。
  答复文本是复核记录的一部分，**只在阶段二读取**。
- **命中率分母口径必须并列**：分别给出「含 L-resolved」与「仅 L-open（未落实）」两个分母与命中率
  （`metrics.denominator` / `aiHitRate` 与 `denominatorExclResolved` / `aiHitRateExclResolved`）；
  只报前者会系统性低估 AI 表现。未提供完整复核集时，不得宣称总体命中率。

### 6.3 AI 审核评分卡（自评 · 表格呈现）

用于**量化 AI 审核与人工复核的差距**：由 AI 自评，不使用图表，**一律用表格呈现**。

| 项 | 口径 |
| --- | --- |
| 级次 | `reviewComparison` 无关的独立字段 `aiScorecard.level`，取值 **初审 / 复审 / 终审**（与台账 `review_level` 受控取值一致，禁自由造词） |
| 六维 | 首轮交付正确性 / 自我纠错与定位 / 增量发现价值 / 覆盖完整性 / 过程纪律与可追溯 / 本轮判断质量（`key` 受控，见 schema enum） |
| 分值 | 0–10，**0.5 的整数倍**；每维必须给 `basis`（打分依据），**禁止无依据给分** |
| 综合分 | `composites.aiOnly`＝六维均值**按 0.5 取整**；`composites.withHumanLoop`＝**复审校正后**六维均值同法计算（两个口径并列，差异即"人机闭环带来的增量"） |
| 审查记录 | `dimensions` 始终保存**初审分**；复审只通过 `corrections[]`（`key/from/to/reason`）**补充与校正**，`from` 必须等于初审分 → **只增不覆盖**，不得改写初审分 |
| 级次约束 | `level=初审` 不得出现 `corrections`/`withHumanLoop`（初审不得事后校正）；`level=复审/终审` 必须给出 `withHumanLoop` 且可复算 |
| 错误项 | `selfAuditErrors[]`：AI **自身**出错记录（`false_positive`/`correction`/`omission`/`wording`；`discoveredAt` 记发现级次）。**初审即产出**（自查所得），复审追加人工指出或在件核验发现的错误 |
| 渲染 | 表格：`维度 × 初审分 × 复审校正 × 最终分 × 打分依据` ＋ 综合分两行 ＋ 校正明细表 ＋ 错误项表；文本只来自受控标签或输入数据（不拼接） |

- **口径来源说明**：知识库《审核统计与台账规范》§1 只定义了 `review_level`（初审/复审/终审）与 A–G 组统计字段，**没有 AI 评分维度与算法**；本节的六维与"均值 0.5 取整"属**技能内受控取值**。若要把分数与错误项纳入台账/氚云字段，需先在知识库登记词表与字段（见 CHANGELOG 的知识库侧待办），技能不擅自回填未登记字段。

## 7 审核范围与未检查项

### 7.1 范围信息

| 项目 | 内容 |
| --- | --- |
| 输入材料 | 本次接收、成功读取和纳入审核的文件清单及版本。 |
| 业务画像 | 对象类型、报告形态、主要角度、评估方法、监管覆盖层及弱结构化标识。 |
| 检查域 | 报告、说明、测算表、数据勾稽、监管覆盖、风险案例等。 |
| 适用性结果 | 已执行、符合、差异、不适用、未检查。 |
| 能力边界 | OCR、公式读取、宏、加密文件、扫描件质量等对审核的影响。 |

### 7.2 未检查项强制字段

| 字段 | 要求 |
| --- | --- |
| itemId | 稳定编号。 |
| item | 未检查的具体对象或要求。 |
| reasonCode | missing_material / unreadable / unsupported / out_of_scope / not_applicable。 |
| reason | 人可读原因。 |
| impact | 对结论完整性或风险判断的影响。 |
| requiredAction | 补材料、人工复核、重新导出或无需处理。 |
| relatedFiles[] | 相关文件；没有则为空数组。 |

“不适用”与“未检查”必须分开：不适用表示经画像或规则适用性判断后明确无需执行；未检查表示本应或可能需要检查但未完成。两者均需写明原因。

## 9 统一 AuditResult JSON 数据结构

AuditResult 是单一事实源。字段名推荐统一使用英文 camelCase，展示文案由受控词典映射。生产环境应维护机器可验证的 JSON Schema，并在编排结束和渲染开始前各校验一次。

### 9.1 顶层结构

```json
{
  "schemaVersion": "1.0.0",
  "auditTask": {},
  "phaseControl": {},
  "summary": {},
  "issues": [],
  "manualConfirmationItems": [],
  "auditBasis": {},
  "reviewComparison": {},
  "scope": {},
  "professionalTrail": {},
  "fileTrace": {},
  "renderPolicy": {}
}
```

### 9.2 推荐字段契约

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| auditTask | projectId, reportVersion, auditTime, engineVersion, profile | projectId 和报告版本不得为空；profile 保留 routeProfile 摘要。 |
| phaseControl | phase1FrozenAt, phase1Digest, reviewAccessedAt, phase2CompletedAt | reviewAccessedAt 必须晚于 phase1FrozenAt。 |
| summary | overallDecision, narrative, counts | counts 必须与 issues 和 manualConfirmationItems 可重算一致。 |
| issues[] | issueId, title, decision, severity, issueType, ruleEvidence, materialEvidence, gapAnalysis, handlingRequirement, recommendedEdits | 规则性缺陷必须同时具备规则证据与材料证据。 |
| auditBasis | rules[], ruleMap, knowledgeBaseFiles[] | 仅列实际使用；规则引用次数可由关联关系重算。 |
| reviewComparison | status, bands, reviewerOnlyItems, metrics | 未执行时 status=not_performed，其他字段不得伪造。 |
| scope | inputs, checkDomains, notCheckedItems, limitations | 所有不可读与未执行项显式记录。 |
| professionalTrail | applicableRuleSnapshot, adjudications, checkRecords, comprehensiveComparison | 默认折叠，但保留完整证据。 |
| fileTrace | generatedAt, rendererVersion, sourceDigest, embeddedJsonDigest | 不得包含绝对路径、nodeId 或凭据。 |

### 9.3 问题对象结构

```json
{

  "title": "可比案例交易时间调整依据不足",
```

### 9.4 关键校验规则

1.  issueId、ruleId、fileId、recordId 在各自作用域内唯一。

2.  decision=fail 且 issueType=rule_defect 时，ruleEvidence 与 materialEvidence 均不得为空。

3.  authorityClass=external_formal 的记录必须包含规则名称、版本状态、具体条款和来源；版本未知时不得宣称“现行有效”。

4.  kbRelativePath 必须是相对路径，拒绝以 /、盘符或 file:// 开头。

5.  manualConfirmationItems 不计入确定性不通过数量。

6.  summary.counts、rules.usageCount 和复核统计必须可由明细重算。

7.  phase2 已完成时，每条阶段一 issue 必须具有 reviewComparison；复核独有项必须进入 reviewerOnlyItems。

8.  HTML 中的可见结论文本必须能逐项映射到 AuditResult，renderer 不得生成新的业务句子。

## 10 HTML 输出规范

### 10.1 自包含与安全

- 输出为 UTF-8 HTML5 单文件，可离线打开。
- CSS 与必要脚本内嵌；不得使用外链字体、样式表、脚本、图片或分析服务。
- 如需图标，使用内嵌 SVG 或纯 CSS；所有动态内容必须进行 HTML 转义。
- 不得出现本地绝对路径、file:// 地址、nodeId、临时目录、访问令牌、API Key、Cookie、连接串、内部主机名或其他凭据。
- 不得从浏览器端向外部地址发送数据；不得包含遥测、埋点或第三方资源。

### 10.2 页面结构与字段清单

| 区域 | 必显字段 | 折叠字段 |
| --- | --- | --- |
| 项目信息 | projectId、reportVersion、auditTime、对象类型、方法、场景、环节、两阶段声明 | engineVersion、routeProfile |
| 审核结果概览 | overallDecision、摘要、问题总数、高中低、待人工确认、未检查数量 | 统计口径 |
| 需要处理的问题 | 标题、编号、严重程度、类型、位置、五段式判定链、处理要求、建议修改文件、流转状态 | 规则编号、置信度、自检、完整证据元数据 |
| 需要人工确认事项 | 标题、位置、客观发现、需确认问题、证据与建议动作 | 内部原因码 |
| 本次审核依据 | 规则名称、正式/内部标签、版本、条款、相对路径、exportedAt、引用次数与用途、规则地图 | 指纹与装载细节 |
| 人工复核对照 | 人话分类、数量、逐项出处与差异 | A/B/C/L 内部编码 |
| 审核范围与未检查项 | 输入材料、检查域、未检查项、原因、影响、动作 | 能力内部标识 |
| 专业审核轨迹 | 折叠标题与摘要 | 规则快照、逐条裁定、审核记录、综合对比 |
| 文件追溯信息 | 生成时间、数据版本、renderer 版本、摘要值 | 无 |

### 10.3 呈现行为

- 问题卡片必须保持规则、材料、差异、结论、修改的固定顺序。
- 高、中、低可使用颜色辅助，但文字标签必须同时存在，不得仅靠颜色表达。
- 专业审核轨迹使用 details/summary 默认折叠；无脚本时仍可访问。
- 空列表显示“本次无此类事项”，不得留下空白标题或隐藏事实。
- 超长路径、规则名和单元格定位允许换行；不得截断影响追溯的内容。

### 10.4 A4 打印

- 使用 @page { size: A4; margin: 16mm 15mm 18mm; } 作为推荐基线。
- 问题卡片尽量避免跨页；过长卡片允许自然分页，不能因强制 break-inside 导致整页空白或内容溢出。
- 表头在跨页时重复；打印时保留严重程度文字和边框。
- 折叠区域的打印策略必须可预测：默认打印员工主体；如启用“含专业轨迹”，应在打印样式中展开对应内容。
- 不得依赖背景色传递唯一信息；黑白打印仍能理解。

### 10.5 可选嵌入 JSON

可将用于本页面的同一份结构化 JSON 嵌入 HTML，便于离线追溯和自动化读取。嵌入内容必须与可见页面同源，并经过与页面相同的数据最小化处理；不得借“隐藏 JSON”夹带页面未展示的额外敏感信息。

```html
<script id="audit-result" type="application/json">
  {"schemaVersion":"1.0.0","auditTask":{},"issues":[]}
</script>
```

- 序列化时必须安全处理 `</script>` 等结束标签风险。
- 建议记录 embeddedJsonDigest，并与渲染输入摘要一致。
- 页面脚本只能读取并展示，不得修改对象后生成新的审核判断。

## 11 流程与两阶段门禁

| 阶段 | 允许读取 | 允许产出 | 禁止事项 |
| --- | --- | --- | --- |
| 阶段一 独立审核 | 被审核材料、项目画像、适用规则与知识库 | 独立意见、规则证据、材料证据、逐条裁定、检查记录、未检查项、阶段一摘要与冻结指纹 | 下载、读取、搜索、引用或根据人工复核记录调整意见。 |
| 冻结点 | 阶段一全部结果 | phase1FrozenAt、phase1Digest、不可变快照 | 冻结后静默改写、删除或重新排序以迎合复核。 |
| 阶段二 复核对照 | 阶段一冻结结果 + 人工复核记录 | 逐条对照、三条带、复核独有项、综合对比与漏检反查 | 把阶段二发现伪装成阶段一命中；无出处匹配。 |
| 发布 | 最终 AuditResult | 单一自包含 HTML 与必要台账回填 | renderer 新增、删除或改写结论。 |

### 11.1 门禁检查

1.  在阶段一工作目录和工具调用层阻断复核材料访问。

2.  阶段一收口时校验所有问题的双证据链和未检查项。

3.  生成不可变摘要，记录冻结时间、输入文件指纹和规则集版本。

4.  只有冻结成功后才向阶段二暴露复核记录。

5.  阶段二匹配必须保留 AI 与复核两端证据。

6.  最终发布前再次校验 Schema、统计一致性、敏感信息和 HTML 完整性。

## 12 版本管理与维护规则

### 12.1 版本对象

| 对象 | 版本字段 | 变更要求 |
| --- | --- | --- |
| AuditResult Schema | schemaVersion | 破坏性字段变更提升主版本；兼容新增提升次版本。 |
| 规则记录 | ruleId + version + exportedAt | 条款或来源内容变化应形成可识别版本，不覆盖历史审核使用的快照。 |
| HTML renderer | rendererVersion | 任何字段映射、排序、打印或转义逻辑变化均记录。 |
| Skill 输出契约 | skillVersion / moduleVersion | 升级前通过契约测试，保证字段完整与枚举合法。 |
| 规范文档 | documentVersion | 记录变更、批准、生效和迁移说明。 |

### 12.2 维护红线

- 不得让叶子 Skill 直接生成最终员工报告或自行定义最终字段。
- 不得让 renderer 基于空字段“智能补写”问题、依据、结论或建议。
- 不得以内部知识库 Markdown 的存在证明其具有法规、准则或监管文件效力。
- 不得在阶段一接触人工复核记录；日志、缓存、文件名和检索结果也属于接触。
- 不得宣称全面检查而隐藏未检查、不可读、降级或空能力。
- 不得把复核独有项删除或归入无关类别以改善命中率。
- 不得在 HTML 或嵌入 JSON 中泄漏绝对路径、节点标识、凭据和超出交付目的的敏感信息。
- 不得使用未经真实读取的条款、原文、页码、坐标、exportedAt 或引用次数。

### 12.3 变更评审清单

- 是否改变员工看到的结论或排序？
- 是否改变权威层级、适用性或证据要求？
- 是否破坏旧 AuditResult 的渲染？
- 是否需要迁移历史数据或重新生成报告？
- 是否覆盖无脚本、离线、A4 和黑白打印场景？
- 是否通过门禁、契约、快照、敏感信息和可访问性测试？

## 13 Skill 与 renderer 维护建议

### 13.1 叶子 Skill

- 只输出本模块的结构化 findings、ruleEvidence、materialEvidence、adjudications 和 checkRecords。
- 使用稳定枚举与标识，不直接输出页面 HTML、CSS 或最终中文章节。
- 对无法检查的项返回结构化 notCheckedItems，不以空数组暗示已通过。
- 原文摘录、数值、文件定位和规则元数据必须来自本次真实读取。

### 13.2 编排与归一化层

- 负责合并、去重、排序、ID 冲突处理和统计重算。
- 负责两阶段权限隔离、阶段一冻结与阶段二对照。
- 负责权威层级映射；无法确认时宁可降为内部辅助或待确认，不得抬高权威性。
- 输出最终 AuditResult 后进入只读状态。

### 13.3 renderer

- 采用确定性模板：同一输入、同一版本应得到语义一致的输出。
- 仅进行转义、受控标签映射、格式化、排序展示和折叠布局。
- 不纠正业务内容；发现不合法数据时拒绝发布并返回校验错误。
- 维护页面快照测试、A4 打印测试、长文本与空状态测试、无 JavaScript 降级测试。

### 13.4 推荐测试

| 测试层 | 至少覆盖 |
| --- | --- |
| Schema 契约 | 必填、枚举、唯一性、条件必填、路径安全、时间顺序。 |
| 门禁 | 阶段一无法访问复核材料；冻结后才开放；摘要不可变。 |
| 证据链 | 规则性缺陷缺任一证据链时失败；两端定位可追溯。 |

### 14.1 编排层调用映射（脚本接入）

调用者唯一：`crwu-audit` 编排层（router）。叶子与下游不得调用校验器/渲染器，也不得自行生成页面或改写结论（§12.2 / §13.1）。

| 编排阶段（router 步骤） | 调用 | 输入 | 输出 | 失败处理 |
| --- | --- | --- | --- | --- |
| 阶段一冻结（步骤 11） | `audit_delivery.py digest <冻结快照.json>` | 阶段一定稿产物快照（AI 意见、route_profile、命中轴、规则/模块清单） | stdout：规范化 JSON 的 sha256（写入 `phaseControl.phase1Digest`；同时记 `phase1FrozenAt`） | 计算失败 → 停止进入阶段二，记 capability gap |
| 阶段二收口 · 交付校验（步骤 14 ①） | `audit_delivery.py validate 审核意见.<项目ID>.json` | 汇总后的 AuditResult JSON | stdout 通过信息；非 0 退出 | **失败即停止交付**，逐条报错；禁止人工绕过、删检查或手改 HTML |
| 阶段二收口 · 渲染（步骤 14 ②） | `audit_delivery.py render 审核意见.<项目ID>.json --out 审核意见.<项目ID>.html` | 同一份 AuditResult JSON | 自包含单文件 HTML；脚本内置**渲染后自检**（`--rendered` 校验、摘要回填） | 校验或自检失败 → 不产出 HTML、退出 1；已存在的旧 HTML 不得充当本次交付 |
| 交付（步骤 14 ③） | 无（文件交付） | `审核意见.<项目ID>.html` | 员工侧唯一交付件；JSON 为内部留档并已嵌入同页 | 渲染不可得 → 记 capability gap，只交付 JSON 与校验错误报告，**不得跳过校验直接出 HTML** |

约定：`digest` 与 `render` 使用同一规范化序列化（排序键、UTF-8、无多余空白），因此冻结指纹可复现、`fileTrace.sourceDigest` 可与冻结摘要互校；脚本仅依赖 Python 标准库，退出码 `0` 通过 / `1` 失败。
