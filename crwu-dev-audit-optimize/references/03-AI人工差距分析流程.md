# references/03 · AI—人工差距分析流程

| 版本 | v0.1 | 状态 | 定稿 | 维护 | crwu-dev-audit-optimize |
| --- | --- | --- | --- | --- |

> 目标：审核结束后，把同一次审核的 AI 结果与人工复核文件逐条对齐，解释 AI 为什么漏检，并把每个
> 仅人工发现项连接到可执行的修复计划。知识库始终只读，知识库修复只能由用户人工完成。

## 1. 输入与同源门禁

必需输入：AI 审核结果、人工复核文件、被审核材料标识、AI 审核时的路由/装配记录，以及同次审核下载的
知识库 `knowledge/` 工作集和 manifest。先核对项目、报告版本、审核批次与材料范围；不能证明同源时，
状态记为 `uncheckable`，不得把差异直接归因于 AI 漏检。

分析使用双基线：

1. **历史基线**：本次审核本地下载的 `knowledge/` + manifest，回答“当时 AI 能看到什么”，用于历史归因；
2. **当前基线**：通过 `crwu-dws` 按已识别的库内层级路径只读下载最新正文，回答“现在是否仍缺”，用于修复建议；
3. 两者不一致时必须分别陈述，禁止用当前知识库反推当时必然存在，也禁止写入知识库。

## 2. 差异对齐与状态

先规范化问题对象、页码/段落、问题类型、事实描述、依据和建议，再做语义匹配：

- `L-resolved`：仅人工文本出现，但 AI 已在别处实质覆盖；非漏检，不进入修复计划；
- `L-open`：人工发现成立且 AI 未覆盖；进入根因分析和修复计划；
- `unclosed`：疑似漏检，但材料或证据不足；列待补证，不生成执行项；
- `uncheckable`：输入不同源或关键文件不可读；列阻塞原因；
- `questionable`：人工意见本身可能不成立；说明反证，不据此修复。

每个差异项使用稳定 ID `L-*`。报告必须保留人工原问题摘要、AI 匹配结果、证据位置、状态、置信度和解释，
不得只给数量。

## 3. 八层追踪与根因

对每个 `L-open` 依次检查：输入可见性 → 画像 → 路由 → 装配 → 知识库正文 → Skill 流程/算法 →
实际执行轨迹 → 输出合并/去重。根因码：

| 根因 | 含义 | 典型修复方向 |
| --- | --- | --- |
| `K1` | 历史与当前知识库均无所需规则/检查点 | 知识库人工补充 |
| `K2` | 当时缺失、当前已补齐 | 回归验证；通常不再修改 |
| `S1` | Skill 未引用或未要求检查已有知识 | Skill 修复 |
| `S2` | Skill 算法、分区、勾稽或输出流程不合理 | Skill 修复 |
| `R` | 画像、路由或能力覆盖缺失 | 路由/结构方案，必要时交 maintainer |
| `I` | 装配路径或范围错误 | 装配/映射方案，交 maintainer |
| `E` | 执行时未完成已定义动作 | 执行约束、回归或提示修复 |
| `O` | 已检出但在输出合并、去重或格式阶段丢失 | 输出逻辑修复 |
| `H` | 人工项已覆盖、不可核验或本身可疑 | 不进入可执行根因统计 |

根因必须引用证据；不能定位时写“待补证”，不得猜测为知识库缺失或 Skill 缺陷。

## 4. `L-*` 与 `FIX-*` 双向关系

每个可执行修复使用稳定 ID `FIX-*`，并满足：

- 每个 `L-open.linkedFixIds[]` 至少包含一个存在的 `FIX-*`；
- 每个 `FIX-*.sourceGapIds[]` 至少包含一个存在的 `L-open`；
- 两侧关系必须完全互反；一个 `L-*` 可对应多个修复，一个 `FIX-*` 可解决多个同因问题；
- `L-resolved`、`unclosed`、`uncheckable`、`questionable` 禁止进入修复计划；
- HTML 同时用明细表、映射表和 `L → 根因 → FIX` ECharts 图展示关系。

## 5. 修复计划与权限边界

修复计划分为两类：

1. `kb_manual`：必须标记 `executionPolicy: manual_only`。逐项给出 `sourceGapIds`、库内目标文档、现有证据、
   缺失内容、建议插入章节/锚点、建议新增的 RULE/CHK 结构、联动文档、人工操作步骤及验证方法。
   本技能与任何 CLI **禁止修改知识库**，也不得生成暗示 AI 已执行知识库写入的提示词。
2. `skill_ai`：给出源仓目标文件、拟修改内容、风险、回归命令和可直接复制给 AI 的修复 prompt。
   prompt 必须列出获批的 `FIX-*` 与 `sourceGapIds`，声明只改批准的源仓文件、知识库只读、不得写运行时目录。
   未获用户明确批准时只展示计划，不生成“立即执行”语义；批准后才可执行。

依赖知识库先补齐的 Skill 修复必须标记依赖门禁，用户未确认人工知识库修复完成前不得执行后续 Skill 项。

## 6. HTML 交付

结构化结果遵循 `scripts/gap_analysis.schema.json`，先校验再渲染：

```bash
python3 scripts/gap_analysis_delivery.py validate --input <gap-analysis.json>
python3 scripts/gap_analysis_delivery.py render --input <gap-analysis.json> --output <gap-analysis.html>
```

模板固定为 `template/gap-analysis-report.html`，ECharts 资源来自本地 `template/echarts.min.js`；输出是离线可打开、
可打印 A4 的单文件 HTML。必须包含：结论摘要、根因与状态图表、仅人工发现明细、八层执行轨迹、差距—修复映射、
知识库人工修复单、Skill 修复 prompt、验证计划。渲染前校验 ID 唯一性、双向映射、权限类型、绝对路径泄露和汇总数。

## 7. 完成判据

- 所有人工项都有状态，所有 `L-open` 都有证据化根因和 `FIX-*`；
- `linkedFixIds[]` 与 `sourceGapIds[]` 双向一致；
- 知识库项全部为 `manual_only`，报告明确目标文档和人工修复方法；
- Skill 项只有在明确批准后才允许 AI 改源仓，并包含回归验证；
- HTML 离线打开正常，表格与 ECharts 均可读，打印时不截断关键映射。
