# 审核条目执行合同

本文件定义维护器写入资产/业务 Skill 的执行要求，不由维护器直接执行正式审核。

## 来源优先级

1. 现行法律法规、执业准则和有效监管规则；
2. 必检项或必检项要点；
3. 历史高频复核问题；
4. 员工审核经验。

低层级内容不能覆盖高层级要求。准则版本、效力或来源冲突时，记录冲突并转人工复核，不形成确定性结论。

## 必检项

命中共性、细分对象或子业务审核文件后，其中每个必检项必须产生一条状态：

| 字段 | 合同 |
| --- | --- |
| `status` | `符合`、`不符合`、`不适用`、`无法核验` |
| `report_evidence` | 当前报告页码、章节、表格或附件位置 |
| `rule_source` | 本次下载文件、实际行号、库内路径、运行时 nodeId、exportedAt |
| `reason` | `不适用`、`无法核验` 时必填 |
| `finding` | `不符合` 时必填，描述当前项目具体问题 |

不得把“未发现问题”作为整份必检项的笼统结果。每项都要有状态；没有材料就标记无法核验并列明缺件。

必检项部分写有“待补”时，登记知识库内容缺口，不根据标题、经验或历史问题自行补造必检要求。

## 历史高频复核问题

命中审核文件中的每个历史问题或问题簇都要检查当前项目，状态为：

- `涉及`：发现当前报告风险迹象，并给出当前项目证据；
- `未涉及`：已检查，当前报告没有对应迹象；
- `无法核验`：材料不足，并列明缺失资料。

历史次数、旧项目名称、案例表述和旧意见只用于提示检查方向。它们不是当前项目事实，也不是现行准则。发现问题时，正式 finding 必须引用当前报告证据和适用规则，不能复制旧意见充当结论。

## 共性与二级条目合并

- 资产：始终执行 `01-共性参考/` 的适用要求，再叠加全部命中细分对象的审核条目。
- 业务：先执行一级业务根目录的 `共同审核点`（若库内存在），再执行全部命中子业务的通用审核要点及其相关文件。
- `共同审核点` 是该一级业务的共用层：命中任一子业务都执行，不因命中集合不同而增删；不得把它记成某个子业务的专属条目。
- 一级根内没有 `共同审核点` 时不记缺口——它是条件性约定；只在维护方案与本次下载 manifest 中如实记录"未发现"。
- 相同检查点稳定去重，但保留全部 `source_skills[]` 和 rule_source。
- 内容冲突并列呈现，交人工判断，不以后加载的文件覆盖先加载来源。

## 能力缺口

以下情形必须留下 gap：目录未完整、递归下载失败、审核文件缺失、必检项待补、规则版本不明、来源冲突、报告证据不足。gap 只影响对应检查，不得让其他可用资产、业务、方法、监管或公共能力停止执行。
